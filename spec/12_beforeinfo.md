# 12 直前情報(スタート展示)を時間を決めて取る

- 作成: 2026-11-06(PM)
- 利用者の要望: 「スタート展示(直前情報)が取りづらい。オッズと同じように時間を決めて取りたい」。
- 現状と問題:
  - 直前情報は Open API の当日ファイルから取っている。更新は約10分ごとで、さらに公式サイトからの遅れがある。
  - **11/04 は 16% のレースしか締切に間に合わず、11/06 は午前中ほぼ全レースが間に合わなかった**。直前版の予想(preview)がほとんど出せない。
  - 日中のジョブは、Cloudflare の dispatcher Worker(`br-yoso-dispatcher`、Cron Trigger)が30分ごとに GitHub Actions を起動している。
- 守ること: 公式サイトへのアクセスは **PC か Cloudflare Worker からだけ**(GitHub Actions からはしない)。間隔は **1秒以上**。規約(大量のアクセスの禁止。07 1章)を守る。費用は無料の範囲。

---

## 1. 方式

```
朝ジョブ(Actions) ── 当日のレース一覧(締切時刻だけ)── R2 schedule/YYYYMMDD.json(小さいJSON)
                                                               │
Cloudflare Worker「beforeinfo」(Cron 5分ごと) ── 読む ────────┘
   └─ 締切の15〜10分前のレースだけ、公式の beforeinfo ページを1回だけ取る(取り直しはしない。2026-11-06 利用者の決定)
   └─ 解析して R2 の非公開領域 beforeinfo/YYYYMMDD/SS-RR.json に保存
   └─ そのtickで1件以上保存したら、GitHub に workflow_dispatch(直前予想の確定ジョブ)を1回だけ送る
Actions「直前予想の確定」── R2 から直前情報を読む(Open API より優先)── 直前版の予想を確定 → 公開
```

### 1.1 対象のページ

- `https://www.boatrace.jp/owpc/pc/race/beforeinfo?rno={R}&jcd={場2桁}&hd={YYYYMMDD}`(1レース1ページ)。
- 載っている項目: 展示タイム、チルト、体重・調整重量、プロペラ・部品交換、スタート展示(進入コース・ST)、気象(天候・風向・風速・気温・水温・波高)。
- **ページの構造は未確認**。C-8 で、PCから1〜2レース分だけ取って(1秒以上の間隔)確認し、本書 3章に追記する。

### 1.2 取得のタイミング

| 回 | 対象 | 条件 |
|---|---|---|
| 1回目 | 締切の **15〜10分前** のレース | 未取得のレース。Cron が5分ごとなので、各レースは必ずこの窓に1回入る |
| 取らない | 窓(15〜10分前)を過ぎたレース・締切後 | 取り直しはしない(Q18)。予想の確定と公開が間に合わないため |

- 公式の直前情報は締切の30〜7分前ごろに出る(02 3章)。**取得は1レース1回だけ**(Q18 の決定)。その時点で未掲載だったレースは `not_posted` / `partial` として保存し、Open API の preview(優先順の (2))で補う。
- 中止・順延のレースは取らない(schedule に入れない)。

### 1.3 当日のレース一覧(朝ジョブが置く)

`R2: br-yoso-data/schedule/YYYYMMDD.json`(非公開)。

```json
{"date": "2026-11-06", "generated_at": "2026-11-06T07:45:00+09:00",
 "races": [{"race_id": "20261106-02-01", "jcd": 2, "rno": 1, "closed_at": "2026-11-06T10:45:00+09:00"}]}
```

- 1日約150レースで約12KB。Worker はこの小さなファイルだけを読む(Open API の約3MBのファイルを Worker で解析しない。CPU 10ms の制限のため)。
- 締切時刻が遅れで変わることがあるので、日中の30分ごとのジョブが Open API から読み直して、変わっていれば上書きする。

### 1.4 直前予想の確定の起動方法(比較と決定)

| 案 | 内容 | 直前情報から確定までの遅れ | Actions の回数/日 | 判断 |
|---|---|---|---|---|
| A | dispatcher の日中の間隔を30分 → 10分に短くする | 最大10分 + ジョブ約5分。締切に間に合わないレースが残る | 約96 | 不採用(遅い・空振りが多い) |
| **B** | **beforeinfo Worker が、保存したtickの最後に `workflow_dispatch` を1回送る** | **1〜2分(起動待ち)+ ジョブ約5分**。締切の10分前に取れば、締切の約3分前までに確定できる | 開催中のtickの数だけ(最大 約150) | **採用** |
| C | A と B の併用 | — | — | 不要。今の30分ごとのジョブを予備として残す |

- GitHub の鍵: **dispatcher(`br-yoso-dispatcher`)と同じ鍵を使う**(Q17 の決定)。新しい Worker の secret に同じ値を設定する。
- B の起動の規則: 1つのtickで何レース保存しても、`workflow_dispatch` は1回だけ(入力に race_id の一覧)。前回の起動から4分未満なら送らない(次のtickでまとめる)。
- Actions 側は `concurrency` のグループで、確定ジョブを順番に実行する(前のジョブの途中で次が来たら、終わってから実行。古い待ちは新しいものに置き換える)。
- 確定ジョブは軽くする: R2 の `state/daily`(10 2.4。約60MB)と当日の直前情報だけを取得し、対象のレースの直前版の予想を確定 → export(当日分) → 公開。全体の所要時間の目標は5分以内。
- GitHub の鍵は dispatcher と同じもの(上記)を Worker の secret に入れる。リポジトリやログには出さない。

### 1.5 Actions 側の扱い

- 直前情報の読み込みの優先順: **(1) R2 の beforeinfo(本書) → (2) Open API の当日ファイルの preview**。同じレースで両方あれば (1) を使う。どちらから取ったかを interim の `pv_source` に残す(**値は `official` / `openapi` / `none`**。艇は展示タイムかスタート展示を公式から取ったら `official`、レースは1艇でも公式なら `official`。詳細は `02` 8章)。**合流するのは確定していない当日の openapi の日だけ**(turnmark・旧APIの日は合流しない)。公式の値は項目ごとに優先、欠場の艇は空、登録番号が出走表と一致しない艇は公式の値を使わない。確定する予想ファイルにも `pv_source` を記録する。
- (1) の値は interim の `pv_*` 列(02 1.2)と同じ単位・意味にそろえる(特徴量担当が対応表を作る)。
- 学習時には、過去日は Open API の確定値(取り直し後)を使う(02 3章4項)。当日の (1) と過去の確定値は、取得時点が違うため値がずれることがある。M は、(1) で作った直前予想の成績を `pv_source` 別に分けて報告する(較正がずれていないかを見る)。
- 公開JSONに載せる範囲は今と同じ(`04` 8.1 の `preview_info`: 展示タイム・展示ST・展示の進入・気象)。**チルト・部品交換・プロペラ・体重は出さない**(特徴量には使ってよい)。

## 2. 負荷と無料枠の見積もり

### 2.1 公式サイトへのアクセス

| 項目 | 見積もり |
|---|---|
| 1日のレース数 | 約144〜160(13場の日)。24場の日は最大288 |
| 1回目 | 1レース1回 = 約150 |
| 2回目 | **行わない**(Q18 の決定)。合計 **約150〜300/日** |
| 1回のtickのリクエスト数 | 5分の窓に締切が入るレースだけ = 多くて5〜8件 |
| 間隔 | 1件ずつ順番に、**1.5秒以上**空ける(`await` で待つ。CPU時間に数えない) |
| 1日の上限 | **300ページ**(既定。環境変数 `DAILY_LIMIT`)。**オッズ中継の上限(300/日)とは別に数える**。超えたらその日は止める |
| 停止 | 公式から **403・429 が返ったら、その日はすべて止める**(R2 に `beforeinfo/YYYYMMDD/_stopped.json`)。3回続けて失敗したときも止める。再開は利用者が手動で(印を消す) |
| 応答時間 | 1ページ約10秒(07 2.1 の実測)。1tick 8件でも約90秒 |

- オッズの取得(07)と合わせても、1日 約450〜600 ページ(どちらも上限300)。逐次・低頻度で、規約の「大量のアクセス」に当たらない量に抑える。

### 2.2 Cloudflare の無料枠

| 制約 | 見積もり | 判断 |
|---|---|---|
| Cron Trigger の数 | dispatcher に加えて1つ(5分ごと)。無料プランのアカウントあたりの上限(数個)の範囲か、R-4 で現在の使用数を確認する。足りなければ dispatcher の Worker に同居させる(同じ Worker の別のスケジュール) | 確認が必要 |
| Worker の起動回数 | 288回/日(5分ごと)。開催の無い時間は schedule を読んですぐ終わる | 余裕 |
| CPU時間 10ms/起動 | schedule(12KB)の読み込みと、HTMLの必要な部分を切り出して正規表現で解析(1ページ数ms以内。07 9.4 と同じ方法)。1tickで8ページあると超えるおそれがあるので、**1tickで解析するのは最大3ページ**にし、残りは次のtickに回す(窓に余裕があるため)。R-4 で計測する | 計測して確認 |
| サブリクエスト 50/起動 | 公式 最大8 + R2 数回 + GitHub 1 | 余裕 |
| R2 の書き込み(Class A。100万/月) | 1日 約300〜600 | 余裕 |
| R2 の読み込み(Class B。1,000万/月) | 288回 × 数回 | 余裕 |
| R2 の容量 | 解析済みJSON 1レース約2KB × 300 = 約0.6MB/日、年 約220MB。HTML は保存しない | 10GB に収まる(10 2.3 の見積もりに追加) |
| KV | 使わない(R2 だけで足りる) | — |

### 2.3 GitHub Actions

- 直前予想の確定ジョブ: 開催中に最大 約150回/日 × 約5分。公開リポジトリの標準ランナーは無料。同時実行は concurrency で1本に絞る。
- 既存の30分ごとのジョブはそのまま(予備)。

## 3. 解析(Python と JavaScript で同じ結果)

- 解析結果のJSON(R2 に保存するもの):

```json
{"race_id": "20261106-02-01", "fetched_at": "2026-11-06T10:32:10+09:00", "minutes_before_close": 12.8,
 "attempt": 1, "status": "ok",
 "weather": {"weather_number": 2, "wind_direction_number": 17, "wind_speed": 0, "wave_height": 0, "air_temperature": 17.0, "water_temperature": 17.0},
 "boats": {"1": {"exhibition_time": 6.62, "tilt_adjustment": 0.0, "weight": 52.0, "weight_adjustment": 0.0,
                 "propeller_new": false, "parts": [], "start_course": 1, "start_timing": 0.17}}}
```

  `status`: `ok` / `partial`(展示タイムかスタート展示の一部が未掲載) / `not_posted`(まだ載っていない) / `failed`。値の単位・コード値は Open API の preview と同じにする(風向・天候のコードは `codes.py`。フライングの ST は負の値)。
- **共通の合成HTML**: `tests/fixtures/beforeinfo/`(収集担当が作る。実物のHTMLはリポジトリに入れず、構造だけを残した合成HTML。07 2.2 の注記と同じ)。未掲載・一部未掲載・フライング(`F.03`)・欠場・前付け(進入が枠番と違う)の例を含める。
- Python(`src/collect/beforeinfo.py` の解析関数)と Worker(`workers/beforeinfo/src/parse.js`)の両方で、同じ fixture と期待値(`*.expected.json`)のテストを通す。
- PC からも同じ解析で取れるようにする(`python -m src.collect.beforeinfo --race <race_id>`。確認用と、Worker が止まったときの予備)。

## 6. 今後の予定: スマホでの再予想(おまけ。定刻取得の稼働後)

利用者の案(2026-11-06 合意): レース詳細を開いたときに直前情報を取り、展示タイム・展示STを含めた予想をスマホで計算し直す。

- 順番: **(1) 本書の定刻取得を先に稼働させる → (2) そのあとで、おまけとして追加する**。
- 位置づけ: **確定した予想ではなく参考値**。成績(実運用)の集計には入れない。画面では「参考(端末で再計算)」と明示し、確定版の予想と並べて表示する。
- 前提(着手前に仕様を詳しくする):
  - 直前情報の取得は、本書の Worker の保存済みのデータ(R2)を中継で読む形を基本にする(公式への追加のアクセスを増やさない)。
  - モデルを JavaScript で動かすための書き出し(LightGBM の木を JSON にして、端末で推論する)。
  - **公開しない特徴量(年齢・体重・チルト・部品交換など)を使わないモデル**が必要(端末に送る入力は公開してよい範囲だけにするため)。精度の差を M が確かめる。
  - 確定版との違い(取得時刻・入力・モデル)を表示する。
