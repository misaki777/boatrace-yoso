# 08 ペルソナと機能の検討・Phase 3a の範囲

- 作成: 2026-11-04(PM)
- 背景: 利用者から「舟券を本気で買う人・予想屋さんなど、使う可能性のある人をペルソナにして欲しい機能を検討し、それを基に仕様化して実装まで進める」と依頼された。3本のペルソナ検討を統合したもの。
- 前提の変化(2026-11-04 時点):
  - アプリ本体は Cloudflare Workers の静的アセットで公開済み(`https://br-yoso.boatrace-yoso.workers.dev`。Cloudflare Access + Google ログインで本人だけが見られる)。`scripts/deploy_pages.sh` が `docs/` から `data-local/` と `app/tests/` を除いて公開する。
  - オッズ中継 Worker(07 9章)は未デプロイ。
  - 11/04 の実運用の照合(117R): 本命の1着率 50.4%、3連単上位5点の回収率 50.5%。**本命を強く推しすぎている**(予測50%以上のレースで、予測の平均69.7%に対し実際は57.4%)。モデル担当が直前モデル(preview)と較正の改善を検証中。
- 利用者は今も本人1人。ペルソナは「欲しい機能を洗い出すための仮の利用者像」で、多人数向けに公開・配信することは前提にしない。

## 3. やらないこと

| 項目 | 理由 |
|---|---|
| **【最優先・利用者の強い指示(2026-11-05)】負けたら次は賭け金を増やす仕組みを一切作らない。過去の収支・連敗・前のレースの結果を、賭け金や配分の計算に一切使わない。マーチンゲール法などの「取り返す」買い方の提案もしない** | 損失の拡大と依存を防ぐため。配分(5.6)の入力は、そのレースの予算・買い目・確率・オッズだけに限る。連敗や収支は警告の表示(09 `warn.*`)にだけ使い、金額の計算には渡さない。コードレビューで必ず確認する |
| 投票の自動化・代行購入 | モーターボート競走法上の問題。本人の判断を挟まない買い方は作らない |
| 予想・オッズの配信・販売、多人数への公開 | 公式サイトの規約(私的使用を超えた頒布の禁止)、景品表示法。本ツールは本人専用 |
| 書き出し・コピーにオッズの数値を入れる | 07 1章の方針(数値は頒布しない) |
| 公式サイトの iframe 埋め込み、トップ以外への直接リンク | 公式サイトのリンク方針 |
| 「勝てる」「おすすめ」などの断定表現、的中だけを強調する演出 | 誤認の防止。外れも同じ重さで見せる |
| 負けを取り返すための賭け金の増額の提案(マーチンゲール等) | 依存・損失拡大の防止 |
| 購入記録・印・メモを公開JSONやサーバーに載せる | 個人の情報。端末内(localStorage / IndexedDB)だけに置く |
| 本人が選んでいない通知 | 通知は本人がオンにしたものだけ |
| LLM による文章生成 | CLAUDE.md の方針(無料・CPUの手法のみ)と、表現の管理のしやすさ |

## 4. 表現のルール(全画面・全書き出し。DA・W・E が守る)

1. **件数を必ず添える**。200R未満の集計は、数字を薄く表示し「件数が少ないため参考程度」と添える。
2. 回収率には **95%信頼区間** を添える(区間が100%をまたぐときは「プラスともマイナスとも言えない」)。
3. **バックテスト(検証)と実運用を必ず区別する**。バックテストで戦略やしきい値を選んだ期間の成績は「後知恵を含む」と明記する(03 6章)。
4. 「おすすめ」ではなく「モデルの上位」「条件に合う買い目」と書く。
5. 的中と不的中は同じ大きさで表示する。
6. 予算・損失上限に近づいたら警告する。上限を超えたあとも記録はできるが、警告は消えない。
7. 深夜(0〜5時)と、連続利用60分ごとに、さりげなく表示する(操作は妨げない)。
8. S5 に、相談窓口(ギャンブル等依存症の相談先)と、20歳未満は舟券を買えないことを書く。

### 5.1 予想の確定(F01)の仕様

現状の弱点: `predict` と `export_day` を同じ日に再実行すると、予想が上書きされる。モデルを入れ替えると、過去日の実運用の成績まで変わってしまう。

1. **確定の単位**: 日 × variant(`pre` / `preview`)。最初に `predict` が書いた `data/predictions/YYYYMMDD_{variant}.parquet` を確定版とする。
2. **M(predict)**: 出力先に同じ日・同じ variant のファイルがあれば、**書き込まずに終了コード 0 で終わる**(「確定済みのためスキップ」と表示)。`--force` を付けたときだけ上書きし、そのときは元のファイルを `data/predictions/superseded/YYYYMMDD_{variant}_{旧model_id}.parquet` に退避する。
3. **確定の印**: 予想ファイルに `locked_at`(最初に書いた時刻)を持たせる(predicted_at と同じ値でよい)。
4. **E(export)**: 公開JSONの `prediction` は確定版から作る。結果(`result`)だけを毎回反映する。過去日の `prediction` を、現在の `models/latest` で作り直すことはしない。
5. **成績(`performance.json` の `live`)** は、各日の確定版の予想だけから集計する。日ごとに `model_id` を残し、モデルの切り替わりがわかるようにする(F40 のモデル更新履歴)。
6. 直前版(preview)は、前日版とは別の確定版として持つ。成績は「前日版」「直前版」を分けて集計する(直前版が始まるまで直前版は空)。
7. テスト: 同じ日に predict を2回実行しても、2回目は確定版を変えないこと。export を何回実行しても `prediction` が変わらないこと。

### 5.2 確率の根拠トップ3(F03)の仕様

- **M**: `predict` で LightGBM の `pred_contrib=True` を使い、各艇の各特徴量の寄与(logit 上の値)を出す。各艇について、**絶対値の大きい上位3つ**を `data/predictions/YYYYMMDD_{variant}_contrib.parquet`(列: `race_id, entry_number, rank, feature, contribution`)に出す。確定(5.1)の対象に含める。
- 特徴量名は、表示用の日本語ラベルの対応表 `src/model/feature_labels.py`(M が作る。例: `national_win_rate` → 「全国勝率」、`h_stadium_course_win_rate_365d` → 「この場・このコースの1着率(1年)」)で変換する。対応が無い特徴量は名前のまま出す。
- 寄与はレース内で正規化する前のスコアに対するものなので、表示は「確率を上げた要因/下げた要因」の向きと相対的な大きさだけにし、パーセントの数値として見せない。
- 特徴量の値も添える(例: 「全国勝率 6.85(上げる要因)」)。ただし出走表に載っている値と、自前で集計した値だけ(公開してよい範囲。04 1章)。

### 5.3 較正・信頼区間・戦略比較(F04・F05)の仕様

- **M**: `src/model/evaluate.py` と `backtest.py` に、次を `reports/` に出す機能を足す。
  - 較正: 1着確率を10の帯(0〜10%、…、90〜100%)に分け、帯ごとに件数・予測の平均・実際の1着率・95%区間(Wilson)。期間ごと(test、実運用の月ごと)。
  - 戦略比較: 戦略ごとに 件数(レース数・点数)、回収率と95%区間(ブートストラップ)、的中率、最大連敗(レース単位)、最大損失(累積収支の最大ドローダウン、円)、`leak_free`。**基準として「1号艇の単勝を買い続ける」「1号艇から3連単の上位5点」**を必ず含める。
- **E**: 実運用(`live`)の較正・戦略比較は、確定版の予想と結果から E が集計する(M の集計関数を import して使う。計算を二重に書かない)。
- 出し先は `performance.json`(04 の追加)。

### 5.4 端末内のデータ(F06・F07)の仕様(W)

- 保存先: **IndexedDB**(購入記録は件数が増えるため。localStorage は設定だけ)。データベース名 `br-yoso`、ストア `bets`(購入記録)、`marks`(印)、`notes`(メモ)、`budget`(予算)。
- 購入記録の1件: `{id, race_id, bet_type, combination, amount(円), bought_at, source: "model"|"self"|"mixed", memo}`。払戻は結果(公開JSONの `result.payouts`)から自動で計算し、保存しない(結果が後で直っても追従する)。返還は返還額として扱う。
- 印: `{race_id, marks: {"1": "◎", "3": "○", …}, updated_at}`。印の成績は「◎が1着になった割合」「◎-○-▲で買った場合の回収率(仮定)」を出す。
- メモ: `{race_id, text, updated_at}`(500文字まで)。
- 予算: 1日・1か月の上限(円)、連敗の警告回数(既定5)。上限の80%と100%で警告。
- バックアップ: JSON ファイルへの書き出しと読み込み(端末を替えるとき用)。CSV は 3b。
- これらは公開JSON・サーバー・Worker に送らない。`deploy_pages.sh` の公開物にも含まれない(端末内にしか無い)。
- 注意: Cloudflare Access のドメインの端末内データは、ブラウザのデータ消去で消える。画面にバックアップを促す表示を出す。

### 5.5 買い目合計(F08)の仕様(W)

- 選んだ買い目について、点数・総額(1点あたりの金額 × 点数、または買い目ごとの金額)を出す。
- オッズがあるとき(手入力・中継 Worker):
  - 合成オッズ = 1 / Σ(1 / odds_i)(同じ金額で買う場合)。
  - トリガミ回避の配分: 各買い目の払戻 ≥ 総額 となるよう、`金額_i ∝ 1/odds_i` で配分し100円単位に切り上げる。全部を満たせないときは「この組合せではトリガミを避けられない」と表示する(賭け金を増やす提案はしない)。
- オッズが無いときは、必要オッズ(1/確率)だけで合計を出し、合成オッズは出さない。
- コピー: テキストで「場名 R番号 券種 組合せ 金額」の形。**オッズの数値・期待値は入れない**。末尾に「個人用の参考情報・的中を保証しない」を入れる。

### 5.6 買い目ごとの金額の配分(F41。2026-11-05 追加、W に依頼済み)

S2 の買い目合計で、**1レースの予算**(100円単位)と**配分のしかた**を選ぶと、買い目ごとの金額を出す。

| 配分 | 計算 | オッズ |
|---|---|---|
| 均等 | 予算 ÷ 点数 | 不要 |
| 上位厚め | 確率の順位で重みを付ける(1位から 3:2:1… のように逓減。重みの表はフロントの定数) | 不要 |
| 確率に比例 | 金額_i ∝ 確率_i | 不要 |
| 払戻をそろえる | 金額_i ∝ 1/オッズ_i(どれが当たっても払戻がほぼ同じ) | **必要** |
| 期待値に比例 | 金額_i ∝ (期待値_i − 1)。**期待値1未満の買い目は0円**。**1点の上限は予算の40%**。合計は予算以内 | **必要** |

共通の規則:
- 金額は100円単位に丸める(切り捨ててから、余りを重みの大きい順に100円ずつ足す)。**合計は必ず予算以内**。予算が点数×100円に満たないときは、重みの小さい買い目を0円にする。
- **入力はそのレースの予算・買い目・確率・オッズだけ**。過去の収支・連敗・前のレースの結果は使わない(3章の先頭)。
- オッズが無いとき、「払戻をそろえる」「期待値に比例」は選べない(理由を表示。09 `alloc.*`)。期待値に比例で、期待値1以上の買い目が無いときは全額0円になり、その旨を表示する。
- 過去データでは、均等・上位厚め・確率比例の回収率はどれも約78%(9月 77.4〜77.7%、10月 78.0〜78.7%)で、**配分で回収率はほとんど変わらない**。画面ではこの点を `help.allocation` で説明し、損の額は賭け金に比例することを伝える。
- 配分の計算はテストケース(予算・確率・オッズ → 金額)で固定する(W。合計が予算以内、上限40%、期待値1未満は0円、過去の収支を引数に取らないこと)。
