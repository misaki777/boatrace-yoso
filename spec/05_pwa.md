# 05 PWA要件定義(docs/)

対象: デザイナー(画面設計・ビジュアル)と、PWAフロント担当(実装)。
このファイルが決めるのは **画面の構成・載せる情報・情報の優先度・操作の流れ** まで。色・フォント・レイアウトの細部・アイコン・印(◎○▲など)の表し方はデザイナーが決める。

---

## 1. 前提

| 項目 | 内容 |
|---|---|
| 利用者 | 本人1人。ボートレースの基本(枠番、コース、3連単など)はわかっている |
| 主な端末 | スマホ(縦向き、幅360〜430px)。PCで見ることもあるが、PC向けの最適化は後回しにする |
| 主な利用場面 | (1) 朝や昼に、その日のレースを一通り見て、狙うレースを決める (2) 締切の数分前に、投票アプリと行き来しながら確認する (3) 夜や翌日に、結果と回収率を振り返る |
| 配信 | GitHub Pages(静的サイト)。サーバー側の処理は無い。データは `docs/data/*.json` を読むだけ(`04_export_json.md`) |
| 更新頻度 | MVPでは1日に数回(手動)。リアルタイムの更新は無い。**画面に「データ更新: 21:05」のように、生成時刻を常に出す** |
| 通信 | 電波の悪い場所でも、前回読み込んだ内容は表示できること(オフライン対応) |
| 技術(フロント担当向けの推奨) | ビルドツールなしの素のHTML/CSS/JavaScript(ES Modules)。外部のライブラリやCDNには原則として頼らない。グラフはSVGかCSSで描く。必要になったら相談する |

## 3. S1 今日のレース一覧(ホーム)

目的: 「次に締め切るレース」と「狙い目のレース」を、すぐ見つけられること。

### 載せる情報(優先度順)

| 優先度 | 情報 | JSONの項目 |
|---|---|---|
| A | 日付、データの更新時刻 | `date`, `generated_at` |
| A | 締切が近い順のレース一覧(締切済みは下に回すか、折りたたむ) | `closed_at`, 端末の時刻 |
| A | 各レース: 場名、R番号、締切時刻、締切までの残り時間 | `stadium_name`, `race_number`, `closed_at` |
| A | 各レース: 本命の艇(p_rank=1 の枠番)と、その1着確率 | `boats[].p_rank`, `p_win` |
| A | 各レース: 堅さ(confidence)が一目でわかる表示 | `confidence` |
| B | 各レース: 推奨買い目の有無と点数(0点なら「見送り」) | `recommended` |
| B | 結果が出たレース: 的中/不的中、払戻額 | `result.recommended_outcome` |
| B | その日の集計(的中数、回収率) | `day_summary` |
| C | 場ごとのグレード、タイトル、何日目か | `grade`, `title`, `day_number` |

**最終日・優勝戦の表示(2026-11-03 決定)**: MVP では「N日目」と、レースの `subtitle`(「優勝戦」「準優勝戦」などの文字列)をそのまま表示するだけにする。最終日かどうかや優勝戦かどうかを判定する専用の項目は JSON に追加しない(開催日数は出走表に無く、最終日は判定できないため)。優勝戦を目立たせたい場合も、フロントで `subtitle` を文字列判定しない(「準優勝戦」と取り違えるため)。必要になったら Phase 2 で、エクスポート側に `race_kind` を追加する(`02_features.md` の `RACE_KIND_CODES` を流用)。

### 堅さの区分(2026-11-03 決定)

`confidence`(1着確率の最大値)を、次の3段階で表示する。しきい値はフロントの定数として持ち、JSONには区分を入れない(Phase 2 で S6 設定から変えられるようにする)。

| 区分 | 条件 |
|---|---|
| 堅 | confidence ≥ 0.50 |
| 中 | 0.35 ≤ confidence < 0.50 |
| 荒 | confidence < 0.35 |

「荒」の下限 0.35 は、サンプルの見送り戦略(`confidence_skip` の alpha=0.35)と同じ値にそろえている。実運用の戦略は `top_k` なので、「荒」でも推奨買い目が出ることがある(表示上の区分と見送りの判断は別物)。

**しきい値は固定とし、戦略の見送りしきい値(alpha)とは連動させない(2026-11-03 決定)**。理由: 実運用の `top_k` には alpha が無い。また、戦略を変えるたびに同じ確率のレースの「堅/中/荒」が変わると、過去日と見比べられなくなるため。見送りかどうかは `recommended` が0件かどうかで別に表示する。

### 操作

- 表示の切り替え: 「締切順(既定)」と「場ごと(場→R の2段)」。
- 絞り込み(Phase 2でよい): 「堅いレースだけ(confidence ≥ 設定値)」「推奨ありだけ」「お気に入りの場だけ」。
- 締切までの残り時間は、端末の時刻で1分ごとに更新する(データを取り直す必要はない)。
- 下に引っ張って再読み込み、または再読み込みボタン。
- **自動の再読み込み(2026-11-03 決定)**: アプリが前面に戻ったとき(`visibilitychange` で `visible` になったとき)、前回 JSON を取得してから5分以上たっていれば、`index.json` と表示中の日の `days/YYYYMMDD.json` を取り直す。5分未満なら取り直さない。一定間隔で定期的に取りに行く処理(ポーリング)はしない。GitHub Pages は `Cache-Control: max-age=600` を返すので、取得には `fetch(url, {cache: "no-cache"})` を使い、ブラウザのキャッシュを毎回検証させる。再読み込みに失敗したときは、表示中の内容を消さずに「更新できませんでした(21:05時点の表示)」と出す。

## 4. S2 レース詳細

目的: 締切前に、買うかどうかと何を買うかを決められること。結果が出た後は、答え合わせができること。

### 載せる情報(優先度順)

| 優先度 | ブロック | 内容 |
|---|---|---|
| A | ヘッダ | 場名、R番号、締切時刻と残り時間、レース名(subtitle)、予想の種類(前日/直前)と予想した時刻 |
| A | 各艇の確率 | 6艇の枠番(枠の色は公式の 白・黒・赤・青・黄・緑 に合わせることを推奨)、選手名、級別、1着確率(棒グラフなど、ひと目で比べられる形)、2着以内・3着以内の確率 |
| A | 推奨買い目 | 組合せ、確率、**必要オッズ**(「このオッズ以上なら期待値プラス」)。0件なら「見送り推奨」と明示する |
| A | 結果(結果があるとき) | 着順(1〜3着)、決まり手、的中した推奨買い目の強調、払戻額 |
| B | 確率上位の一覧 | 単勝(6点)、2連単(上位10点)、3連単(上位20点)を券種タブで切り替える。各行に確率と必要オッズ |
| B | 選手の補足 | 支部、全国勝率、当地勝率、モーター2連率、平均ST、F数(F持ちは目立たせる) |
| B | 直前情報(直前予想のとき) | 展示タイム(レース内で最速を目立たせる)、展示の進入コース(枠番と違えば目立たせる) |
| C | 確定オッズでの期待値(翌日以降) | 推奨買い目の確定オッズと期待値 |
| C | 前後のレースへの移動 | 同じ場の前・次のR |

### 必要オッズの見せ方(重要)

- 当日はオッズを取得していないため、画面にはオッズも期待値も出せない。代わりに必要オッズを出し、利用者が投票アプリのオッズと見比べる。
- 「必要オッズ 19.3倍 → 投票アプリでこれより高ければ買い」という意味が直感的に伝わる表現を、デザイナーに検討してほしい。

### S7 オッズ入力→期待値(Phase 2)

- 推奨買い目や確率上位の行で、オッズを入力できるようにする(数字キーボード、小数1桁)。
- 入力するとすぐに `期待値 = 確率 × オッズ` を表示し、1.0以上かどうかを色や形で区別する。
- 入力値は、その端末の localStorage に race_id ごとに保存する(サーバーには送らない)。

## 5. S3 成績

目的: このモデルと買い方が、本当に効いているかを確かめること。

| 優先度 | 情報 | JSONの項目 |
|---|---|---|
| A | 実運用の累計: 回収率、的中率、投資額・払戻額(1点100円と仮定) | `performance.live.total` |
| A | 日ごとの回収率の推移(累積回収率の折れ線と、100%の基準線) | `live.by_day` |
| B | 月別の表 | `live.by_month` |
| B | バックテストの成績(戦略ごとの回収率と95%区間)。`leak_free:false` は「参考値(後知恵)」と明示する | `backtest` |
| C | モデルの情報(model_id、学習期間) | `backtest.model_id` |

注意書き: 「回収率はシミュレーションであり、将来の成績を保証しない」を常に表示する。

中止レースは回収率・的中率に含めない(買わなかった扱い。`04_export_json.md` 4章・5章で決定済み)。見送りのレースも含めない。必要なら注記として「中止・見送りのレースは集計に含みません」を添える。

## 6. S4 日付の選択

- `index.json` の `dates` から選ぶ。既定は `latest_date`。
- 各日付に、その日の回収率と状態(予想のみ/途中/確定)を小さく添える。

## 7. S5 このアプリについて

- 非公式データに基づく個人用の参考情報で、正確性は保証しないこと。
- データの出典(`index.json` の `sources`)とライセンスの表記。
- 舟券の購入は自己責任であること。20歳未満は購入できないことの注記。
- モデルの概要(LightGBM、Harville)を1〜2文で。

## 9. 非機能要件

| 項目 | 要件 |
|---|---|
| PWA | `manifest.webmanifest`(名前、アイコン 192/512px、`display: standalone`)、Service Worker。アプリ名(`name`/`short_name`)は利用者が決める(未決事項U11)。決まるまでは `design/visual/README.md` の仮の名前(「ボートレース予想」/「BR予想」)を使う。**iOS 用のスプラッシュ画像は MVP では作らない**(Android は manifest の `background_color`・アイコン・名前から自動で作られる。iOS は起動時に白い画面が一瞬出るが、許容する) |
| キャッシュ | アプリ本体(HTML/CSS/JS/アイコン)はキャッシュを優先する。`docs/data/*.json` はネットワークを優先し、失敗したらキャッシュを使う。キャッシュを表示しているときは「オフライン表示中(21:05時点)」と出す |
| 表示速度 | 4G回線で、ホームの最初の表示が2秒以内 |
| 時刻 | すべてJSTで表示する。端末のタイムゾーンが異なっても、JSTで表示すること |
| アクセシビリティ | 色だけで情報を伝えない(的中・期待値≥1 などは、形や文字も併用する)。タップ領域は44px以上 |
| エラー | JSONが読めない、スキーマのバージョンが違う、などの場合は、わかる言葉で表示し、再読み込みの手段を出す |
| パス | GitHub Pagesのサブパス(`/boatrace-yoso/`)で動くよう、すべて相対パスにする |
| 開発用 | `?data=sample` を付けると `docs/data/sample/` を読むようにする |
