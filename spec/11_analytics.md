# 11 データ分析(7機能)

- 作成: 2026-11-05(PM)。利用者が「データ分析」の7機能の実装を決めた。
- 条件:
  - 費用は無料の範囲(GitHub Actions の公開リポジトリの無料枠、Cloudflare の無料枠)。
  - **オッズの数値は公開JSONに出さない**(07 1章)。**購入記録は端末の外に出さない**(08 5.4)。
  - 禁止事項は従来どおり(08 3章の先頭: 過去の収支・連敗・前のレースの結果を賭け金や配分の計算に使わない)。
  - **件数の少ない集計は薄く表示し「参考」と添える**(08 4章。しきい値は 1.3)。
  - **重い集計は GitHub Actions の中で事前計算し、スマホには結果の表だけを送る**。
  - 今は約10か月分のデータで作り、**10年分(2016-08〜。10 2章)が入ったら、同じコマンドで作り直すだけで済む**作りにする(期間を決め打ちしない。データの開始日・終了日は interim から読む)。
  - **日次の更新ジョブを重くしない**。集計は前日確定ジョブ(1:12)、週1、月1のどれかで更新する。

## 1. 共通の設計

### 1.1 データの流れ

```
interim(races・entries・payouts。全期間) ┐
確定版の予想(data/predictions。実運用)   ├─ src/features/analytics/*.py(F)  → data/analytics/*.parquet(中間。git管理外)
style 集計・履歴の状態(F-6・F-8)       ┘  src/model/analytics_eval.py(M)  ↗
                                                      │
                                       src/export/export_analytics.py(E)
                                                      ▼
                                  docs/data/analytics/*.json(公開。結果の表だけ)
                                                      ▼
                                  PWA の「分析」タブ(W)。自分の収支(5)は端末内だけで計算
```

- 期間は「データの最初の日〜前日」を自動で読む。10年分が入ったら、月1ジョブ(または手動)で全部を作り直す。
- 払戻(配当)は結果の払戻金で、オッズの数値ではない(公開してよい。07 1章)。**締切前オッズ・確定オッズの数値は、どの集計にも出さない**(期待値ランクの区分だけは可)。

### 1.2 公開ファイルとサイズの上限

| ファイル | 機能 | 更新 | gzip後の上限 |
|---|---|---|---|
| `docs/data/analytics/index.json` | 一覧・更新時刻・データ期間 | 各集計の更新時 | 5KB |
| `docs/data/analytics/stadiums.json` | 1 場の傾向 | 前日確定ジョブ | 100KB |
| `docs/data/analytics/cube/{stadium}.json`(24ファイル) | 2 条件で集計 | 週1 | 1ファイル 60KB、合計 1MB |
| `docs/data/analytics/rankings/YYYYMMDD.json` | 3 ランキング | 朝の予想確定ジョブ(当日分) | 50KB |
| `docs/data/analytics/model_weakness.json` | 4 モデルの弱点 | 前日確定ジョブ | 80KB |
| `docs/data/analytics/simulator.json` | 6 シミュレーター | 週1(検証)・前日確定(実運用) | 150KB |
| `docs/data/analytics/weekly/YYYY-Www.json` | 7 週ごとのまとめ | 週1 | 1週 20KB |

- エクスポートは書き出しの前にサイズを測り、**上限を超えたら失敗させる**(黙って大きなファイルを出さない)。超えたら次元・行を減らすよう PM に相談する。
- スマホは「分析」タブで、必要なファイルだけを開いたときに読む(遅延読み込み)。
- 選手名は公開してよい(U3)。年齢・体重など 04 1章で出さないと決めた項目は出さない。

### 1.3 件数の扱い(全機能共通)

| 件数(レース数、または出走数) | 表示 |
|---|---|
| 200 以上 | 通常 |
| 30〜199 | 薄く表示し「参考」 |
| 30 未満 | 数字を出さず「件数不足」(公開JSONにも率を入れず、件数だけ入れる) |

- 率には件数を必ず付ける。回収率には95%区間(レース単位のブートストラップ。前日確定ジョブでの計算量を抑えるため、回数は 200 回)。
- 率の区間は Wilson。
- 定数は `src/common/analytics_rules.py`(P が作る。F・M・E・W の全員がこれに合わせる。W は同じ値を定数で持つ)。

### 1.4 所要時間の見積もり(10年分 = 約5.5万レース/年 × 10)

| ジョブ | 追加する処理 | 10か月分 | 10年分 |
|---|---|---|---|
| 前日確定(1:12) | 1 場の傾向、4 モデルの弱点、6 の実運用分 | 1分未満 | 約3〜5分(interim-full の取得 約1分を含む) |
| 朝の予想確定(7:41) | 3 ランキング(当日の出走選手だけ。履歴の状態 F-8 から) | 数秒 | 数秒 |
| 週1(新設。**月曜 3:00 JST**。cron は UTC で `0 18 * * 0`(日曜 18:00 UTC)) | 2 キューブ、6 の検証分のグリッド、7 週ごとのまとめ | 約2分 | 約15〜25分 |
| 月1(10 2.5) | 全部の作り直し(10年分の取り込み直後もこれ) | — | 週1の分を含めて +約30分 |

- 30分ごとの更新ジョブには何も足さない。
- 前日確定ジョブは interim-full(約170MB。10 2.4)を必要とするので、取得は前日確定ジョブだけにする(更新ジョブは今のまま `daily` の状態だけ)。

## 2. 機能ごとの仕様

### 2.1 場の傾向(A1)

`stadiums.json`: 24場それぞれについて、全期間と直近365日。

| 項目 | 内容 |
|---|---|
| コース別1着率 | コース1〜6(本番の進入コース)の1着率・2連対率・3連対率、件数 |
| 決まり手の割合 | 逃げ・差し・まくり・まくり差し・抜き・恵まれ |
| 季節 | 春(3〜5月)・夏(6〜8月)・秋(9〜11月)・冬(12〜2月)ごとの、コース1の1着率と決まり手の割合 |
| ナイター | 締切時刻 17:00 以降のレースとそれ以前の比較(ナイター開催の場だけ) |
| 風 | 風の区分(追い風・向かい風・横風・無風。`codes.wind_class`)× 風速の区分(0〜2m・3〜5m・6m以上)ごとの、コース1の1着率と決まり手の割合。**本番の気象(result)を使う**(過去の傾向の集計なので、予測の特徴量とは違いリークの問題は無い) |
| 荒れやすさ | 3連単の払戻の平均・中央値、**万舟率**(3連単の払戻が10,000円以上のレースの割合)、1号艇1着率 |
| 全国との差 | 全国平均との差(コース1の1着率、万舟率) |

### 2.2 条件で集計(A2。事前計算のキューブ)

組み合わせが爆発しないよう、**場ごとのファイルに分け、次元を絞り、件数の少ない行を落とす**。

- 単位: 出走(1行=1艇。率は艇単位)と、レース単位の値(決まり手・払戻)を同じ行に持つ。
- **次元**(すべて少数の区分にする):

| 次元 | 区分 | 数 |
|---|---|---|
| 場 | ファイルを分ける | (24ファイル) |
| コース | 1〜6(本番の進入) | 6 |
| 風 | 追い・向かい・横・無風 × 弱(0〜2m)・中(3〜5m)・強(6m以上)。無風は1区分 | 10 |
| 級別 | A1・A2・B1・B2 | 4 |
| グレード | SG/PG1/G1 をまとめて「上位」、G2/G3、一般 | 3 |
| 季節 | 春・夏・秋・冬 | 4 |

- **事前計算するのは、よく使う切り口の組合せだけ**(全次元の掛け合わせ 6×10×4×3×4 = 2,880 行/場 は作らない):
  - コース単独、コース×風、コース×級別、コース×グレード、コース×季節、コース×風×級別
  - 各次元には「すべて」の値も持つ(画面で選ばない次元は「すべて」)
  - 1場あたり 約 6 + 60 + 24 + 18 + 24 + 240 ≒ **約370行**
- 値: 件数(出走数・レース数)、1着率、2連対率、3連対率、決まり手の割合(1着艇の決まり手)、3連単の払戻の平均・中央値。
- **件数の下限**: 出走数 30 未満の行は、率を入れず件数だけ(1.3)。
- 画面で選べない組合せ(例: 風×級別×季節)は「事前計算していない組合せです」と表示する(その場で計算はしない)。
- 期間: 全期間と直近3年の2つ(10年分が入ったあとの古い傾向の影響を見るため)。今は両方とも同じ期間になるので、データが3年未満の間は「全期間」だけを出す。

### 2.3 選手・モーターのランキング(A3)

`rankings/YYYYMMDD.json`(朝の予想確定ジョブで当日分を作る。2日分だけ保管)。対象は **今日の出走表に載っている選手・モーター**。

| ランキング | 値 | 範囲 |
|---|---|---|
| コース別の逃げ率 | 今日コース1に入る予定の選手の、コース1での逃げ率(style の縮小後の値と件数) | 全場・場ごと |
| 平均ST | style の平均ST(全コース) | 同上 |
| まくり・差しの率 | コース2〜4の選手の差し・まくり率 | 同上 |
| モーター2連対率 | 出走表のモーター2連率と、今節(D−1まで)の2連対率 | 場ごと |
| 今節の成績 | 今節の平均着順(D−1まで) | 場ごと |

- 上位10件ずつ。件数30未満は対象外にする(ランキングに出さない)。
- 選手カード(10 4章)へのリンク。

### 2.4 モデルの弱点分析(A4)

`model_weakness.json`(前日確定ジョブ)。**実運用の確定版の予想だけ**を使う(08 5.1)。バックテストの値は混ぜない(別のタブ・別のキー)。

| 項目 | 内容 |
|---|---|
| 条件別の外れ方 | 場・確率帯(本命の確率の10%刻み)・決まり手(結果)・天候・風の区分・版(前日/直前)ごとに、本命の1着率、予測の平均、差、logloss、件数 |
| 較正の推移 | 週ごと・月ごとの較正の誤差(ECE)と、確率帯ごとの予測と実際(10 2.5 と同じ定義) |
| 推しすぎの推移 | 「本命の予測が50%以上」のレースの、予測の平均と実際の1着率(週ごと)。11/04 の照合で見つかった問題(予測69.7%に対し実際57.4%)が改善しているかを見る |
| モデルの切り替え | `models.json`(10 2.5)の切り替え日を推移のグラフに縦線で入れる |

- 計算の関数は M(`src/model/analytics_eval.py`。M-11 の較正・区間の関数を使う)、集計の実行と JSON 化は E。

### 2.5 自分の収支分析(A5。端末内だけ)

- **W が端末内(IndexedDB の購入記録 08 5.4)だけで計算する**。サーバー・公開JSON・Worker に送らない。
- 切り口: 券種別、場別、時間帯別(締切時刻で 〜12時・12〜17時・17時〜)、期待値ランク別(購入時に記録したランク。ランクが無い記録は「なし」)、配分のしかた別(08 5.6。購入時に記録する)、印あり/なし別。
- 値: 購入額、払戻、回収率と95%区間(端末で計算できる回数として 200 回のブートストラップ)、的中率、件数。1.3 の件数の扱い。
- 購入記録に `ev_rank` と `allocation` を記録時に保存する(W-11 の項目に追加)。
- この集計の結果を、過去の収支に応じて賭け金を変える提案に使わない(08 3章の先頭)。

### 2.6 買い方のシミュレーター(A6)

`simulator.json`: 事前計算した戦略のグリッドの成績。画面では条件を選ぶと、該当する行を表示する。

- **グリッド**(1回の計算で全組合せを評価する):

| 軸 | 値 | 数 |
|---|---|---|
| 券種 | 単勝・2連単・3連単 | 3 |
| 点数 k | 単勝 1・2、2連単 1・3・5、3連単 1・3・5・10 | (券種ごと) |
| 見送り | なし・荒なら見送り・中以下なら見送り | 3 |
| 配分 | 均等・上位厚め・確率比例(オッズが要らないものだけ) | 3 |

  合計 (2+3+4) × 3 × 3 = **81 通り**。
- 値: レース数、点数、回収率と95%区間、的中率、最大連敗、最大損失(累積収支の最大ドローダウン。1レース1,000円の予算と仮定)、`leak_free`。
- **期間を分ける**:
  - 「検証」: バックテスト(過去データ。モデルが学習に使っていない期間だけ。10 2.5 のウォークフォワードの valid を月ごとにつないだもの)。**「後知恵を含む」の注意を必ず付ける**(条件を見てから選ぶと、たまたま良かったものを選びやすい)。
  - 「実運用」: 確定版の予想だけ。件数が少ない間は 1.3 で薄く表示。
- 期待値を使う条件(期待値ランクで絞る)は、締切前オッズが貯まったら追加する(M-8 のフォワードテストの結果を使う)。それまでは確定オッズでの計算を出さない(後知恵が大きいため)。
- 表示では、**並び替えの既定を「回収率の高い順」にしない**(偶然良かった条件を上に出すため)。既定は「券種 → 点数」の順。「最適」「おすすめ」は使わない(09)。
- 計算は M(`src/model/backtest.py` の戦略の計算を流用。配分は 08 5.6 と同じ規則。W の配分のテストケースと Python で同じ結果になること)。

### 2.7 週ごとの成績まとめ(A7)

`weekly/YYYY-Www.json`(ISO週。月曜〜日曜)。週1ジョブ(月曜 3:00 JST)で前の週の分を作る。過去の週はファイルとして残す(1週 20KB 以内。年 約1MB)。`analytics/index.json` に週の一覧。

| 項目 | 内容 |
|---|---|
| 本命の当たり | 予想の確率帯(〜35%・35〜50%・50%〜)ごとの、本命の1着率と予測の平均、件数。前日版・直前版別 |
| 券種別の回収率 | 既定の戦略と基準(1号艇)の、単勝・2連単・3連単の回収率・的中率・区間 |
| 展開予想の当たり具合 | 決まり手の確率の logloss、最も確率の高い決まり手の的中率、基準(場の決まり手の比率)との比較 |
| 較正 | その週の ECE と、確率帯ごとの予測と実際 |
| 前の週との比較 | 主要な数値の差(件数が少ない週は「参考」) |

- 自分の収支の週のまとめは、端末内で W が同じ週の区切りで出す(公開JSONに入れない)。
