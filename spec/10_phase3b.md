## 1. 自動実行が止まったときの知らせ

### 1.1 仕組み

- **CI(各ジョブの最後)**: 成功したら `docs/data/status.json` を書き、公開物に含める(コミットは今のまま1日2回でよい。Workers の静的アセットへの公開は毎ジョブ行っているため、公開側は毎回新しくなる)。

```json
{
  "schema_version": 1,
  "last_success_at": "2026-11-05T14:04:31+09:00",
  "job": "update",
  "next_expected_by": "2026-11-05T14:34:00+09:00",
  "models": {"pre": "pre_20261104_db90", "preview": "preview_20261104_0b0e"}
}
```

  `job`: `morning` / `update` / `finalize` / `monthly`。失敗したジョブは書かない(前回の成功時刻のまま残る)。URL や実行IDなど、内部の情報は入れない。

- **フロント**: アプリを開いたとき・前面に戻ったとき(05 3章の5分ルールで取り直したとき)に `status.json` を読む(無ければ `index.json` の `generated_at`)。
  - **開催時間中**だけ判定する: 当日の `days/YYYYMMDD.json` の締切時刻の「最初 − 60分」〜「最後 + 60分」の間。当日のファイルが無い、または開催が無い日は判定しない。夜間も出さない。
  - `今 − last_success_at > 90分` なら、画面上部に帯を出す(文言 `09` `stale.*`)。帯には最終更新の時刻を出す。閉じられるが、次に開いたときにまだ古ければまた出す。
  - しきい値90分はフロントの定数(30分ごとのジョブが2回続けて失敗した状態に相当)。
- **README**: GitHub の失敗メール通知(既定でオン。Settings → Notifications → Actions で「失敗したワークフローのみ」を確認)と、Actions のページで失敗したジョブを見る方法、手動で再実行する方法を書く。

## 2. 10年分のデータの取り込みと毎月の作り直し

### 2.1 旧APIからの取得(C-7。PCで夜に分けて実行)

- 対象: `https://boatraceopenapi.github.io/{programs,previews,results}/v3/YYYY/YYYYMMDD.json`、2016-08-01〜2025-12-31(約3,440日 × 3ファイル ≒ **約1.03万リクエスト**)。v3 のスキーマは各リポジトリの `docs/schema.md`(01 1章)。
- 間隔 **1.5秒以上**、1日分(3ファイル)をまとめて取り、既に取った日はスキップ(01 4章の規則)。`--max-requests` を1晩 4,000 程度にして **3晩に分ける**(1晩 約2時間)。
- **GitHub Actions からは取らない**(PCだけ)。保存先: `data/raw/legacy/{programs,previews,results}/YYYY/YYYYMMDD.json.gz`。取得ログは既存の `_fetch_log.jsonl`。
- 2026-01-01 以降は turnmark / openapi を使い続ける(旧APIと重ねない)。

### 2.2 interim への変換(F-7)

- `build_interim` に旧APIの読み込みを足し、**turnmark/openapi と同じ列**の races / entries / payouts に合流させる(`source = "legacy"`)。odds は無い(旧APIにオッズは無い)。
- 列名の違い(例: `number` → `race_number`、`racer_boat_number` → `entry_number`、`racer_place_number` → `place_number`)は変換表で対応し、テストで固定する。
- 旧APIに無い項目(`preview` の `propeller`・`parts` など)は null。中止レース・同着・返還の扱いは 02 1章と同じ。
- 期間の境目(2025-12-31 と 2026-01-01)で、同じレースが二重にならないこと、選手番号・場番号の意味が同じことを確かめる。

### 2.4 毎日のジョブを軽くする(F-8・CI-2)

**方針: 毎日のジョブは生データを落とさない。** 当日の予想に必要なのは、(a) 当日の出走表・直前情報(openapi から取る)、(b) D−1 までの履歴の集計、(c) モデル、だけ。

- **F-8 履歴の集計の状態(スナップショット)**: H・style 特徴量に必要な「キーごとの累積の合計」(02 3章・7章の `window_sum` が使う日ごとの累積)を、**D−1 時点の状態**として `data/history/state_YYYYMMDD.parquet` にまとめる。
  - 累計(`_all`)は「キーごとの累積値」だけを持つ。
  - 期間の窓(90日・180日・365日)は、窓の分の日ごとの合計(直近365日分)を持つ。
  - 当日の H 特徴量は「状態 + 当日の出走表」から計算する。**全履歴から計算した値と完全に一致すること**をテストで保証する(学習時と予想時の特徴量のずれを防ぐ)。
  - 前日分が確定したら(1:12 のジョブ)、状態を1日分進める(前日の結果を足し、窓から外れた日を引く)。
- **CI-2 状態の分け方**:

| R2 のキー | 中身 | 毎日のジョブ | 月1のジョブ |
|---|---|---|---|
| `state/daily.tar.gz` | 履歴の集計の状態、直近400日の interim、当日・前日の raw(openapi)、確定済みの予想(直近)、models/latest | 取得・保存 | 取得 |
| `state/interim-full.tar.gz` | 全期間の interim(約170MB) | 取らない | 取得・保存 |
| `archive/legacy/*` | 旧APIの raw | 取らない | 取らない(interim を作り直すときだけ PC から) |
| `state/models/` | 全モデル(候補を含む)と `history.json` | latest だけ | 取得・保存 |

  - 毎日のジョブが落とす量: 約108MB → **約60MB**(10年分を入れても増えない)。
  - **1ジョブの所要時間(見積もり)**: R2 の取得・展開 約1分、openapi の取得 数秒〜10秒、interim の当日分・特徴量(状態から)約1分、予想 数十秒、export 約1分、保存 約1分 → **合計 約5分(上限30分に十分収まる)**。CI-2 で実測し、10分を超えたら PM に報告する。

### 2.5 毎月の作り直し(M-13・CI-3)

- **起動**: `.github/workflows/monthly.yml`。毎月2日 3:23 JST(前月分の確定のあと。利用の少ない時間)と、手動(`workflow_dispatch`)。
- **手順**(variant ごと。`pre`・`preview`、採用中なら v2 も):
  1. 全期間の interim から特徴量を作る(10年分。約20〜30分の見込み)。
  2. **期間の分け方(ウォークフォワード)**: 前月を M−1 とする。
     - train: データ開始(2016-08 + warm-up 90日)〜 M−2 の末日
     - valid: M−1 の1か月(early stopping、温度T、Harville の γ を決める)
     - 固定の test 期間は置かない。**「次の1か月の実運用(確定版の予想)」が test の役割**を果たし、翌月の作り直しのときに比べる。
  3. 候補モデル(valid で選んだ設定)を、M−1 の末日までのデータで学習し直す(木の数は valid で決めた数の1.1倍)。
  4. **切り替えの基準**(すべて満たしたときだけ `models/latest` を候補に切り替える):
     - (a) M−1 の valid で、候補の `win_logloss` が今の latest より **0.002 以上良い**
     - (b) 同じく `trifecta_logloss` が悪化していない
     - (c) 較正: 10帯の予測と実際の差の加重平均(ECE)が悪化していない
     - (d) 直近の実運用: M−1 の実運用のレース(確定版の予想があるレース)で、候補が出したはずの確率を後から計算したとき、`win_logloss` が latest の確定版より悪化していない
     - (e) 学習が正常に終わった(特徴量の欠損率、行数、予測の合計=1 の検査を通る)
     - どれかを満たさなければ切り替えず、候補は記録だけ残す。
  5. **確定版の予想は書き換えない**(08 5.1)。切り替えは翌日の朝のジョブから効く。
- **切り替えの記録 `models/history.json`**: `[{"date": "2026-12-02", "variant": "pre", "candidate": "pre_20261202_xxxx", "adopted": true, "train_to": "2026-10-31", "valid": "2026-11", "metrics": {"win_logloss": {"candidate": 1.301, "latest": 1.305}, "...": "..."}, "reason": "基準 a〜e を満たした"}]`。
  - E がこれを `docs/data/models.json` に写す(数値は指標だけ。特徴量の一覧や内部のパスは出さない)。アプリは S5「このアプリについて」に「モデルの更新履歴」として表示する(F40)。
- **学習時間の見積もり**: 10年分は約330万艇行 × 約130列(float32 で約1.7GB)。GitHub の公開リポジトリの標準ランナー(4 vCPU・16GB)で、LightGBM 1モデル約5〜15分。variant 2〜4 × 候補の学習と学び直し = 約20〜60分。特徴量の作成 約30分を足して **合計 約1〜1.5時間**。ジョブの上限6時間・公開リポジトリの無料枠に収まる。メモリが足りないときは、学習に使う期間を直近5年に絞る(M-13 で実測して決める)。
- 展開予想モデル(3章)も同じジョブで作り直す。

## 3. 展開予想(決まり手の確率)

### 3.1 モデル(M-14)

- **1行 = 1レース**、目的変数 = `technique_number`(1 逃げ、2 差し、3 まくり、4 まくり差し、5 抜き、6 恵まれ)。LightGBM の `objective=multiclass`、6クラス。中止・決まり手が null のレースは外す。
- 特徴量(F-9 が作る。`data/features/tenkai_{variant}.parquet`): **予定コースごとに並べ直した**各艇の値(コース1〜6 × 主な特徴量: 全国勝率、級別、平均ST、style の `h_cs_nige/sashi/makuri/makurisashi_all`・`h_cs_st_mean_all`・`h_racer_f_rate_all`・前付け率、モーター2連率)、レースの値(場、グレード、レースの種類)、R の style 列(`r_sty_*`)。直前版は展示タイム・展示の進入・展示ST・風(`pv_wind_class`・風速)・波高を足す。
- 前日版・直前版の両方を作る。リーク防止は 02 3章と同じ(D−1 までの結果だけ)。
- 評価(valid/test):
  - 多クラスの logloss、クラスごとの較正(10帯)
  - **基準**: (B0) 全体の決まり手の比率、(B1) 場ごとの決まり手の比率(D−1 までの累計)。LightGBM は B1 より logloss が良くなければ採用しない
  - 整合の確認: 「逃げ」の確率と、着順モデルの「予定1コースの艇の1着確率」の差の分布を報告する(大きくずれるなら表示の方法を PM と相談)
- 出力: `data/predictions/YYYYMMDD_{variant}_tenkai.parquet`(列: `race_id, p_nige, p_sashi, p_makuri, p_makurisashi, p_nuki, p_megumare`)。**確定の対象に含める**(08 5.1)。

### 3.2 公開JSON(E-13)

`prediction.tenkai`(04 に追加):

```json
"tenkai": {"nige": 0.552, "sashi": 0.161, "makuri": 0.142, "makurisashi": 0.098, "nuki": 0.039, "megumare": 0.008, "course1_entry": 1}
```

- 小数3桁、**合計1**(丸めた後の差は最大の項目で調整する)。`course1_entry` は予定1コースの艇の枠番(前日版は1、直前版は展示の進入で決まる)。
- サイズ: 1レース約0.12KB、150レースで約+18KB(gzip後 約+3KB)。

### 3.3 表示(DA-6・W-15)

- S2 に「展開予想」ブロック: 「1コース(◯号艇)が逃げる確率 55%」を大きく、差し・まくり・まくり差しを並べ、抜き・恵まれは「その他」にまとめてよい。
- 前日版/直前版の別と確定時刻を添える。件数・較正の確認先(S3)へのリンク。
- 注意書き: 着順の確率とは別のモデルで計算しているため、数字が一致しないことがある(`09` `tenkai.*`)。

### 3.4 拡張(2026-11-07 利用者の決定)

#### A 誰の決まり手か(M)
- レース単位で、**1着の艇の予定コース(1〜6)× 決まり手(6種類)の同時確率**(最大36通り。ありえない組合せ、例: 2コース以降の「逃げ」は0)。
- 作り方は M が決める(例: 多クラスの目的変数を「コース×決まり手」にする、または着順モデルの1着確率 × コースごとの決まり手の条件付き確率)。合計1。
- 周辺の和が 3.1 の決まり手の確率と、着順モデルの予定コースの1着確率に近いことを報告する(大きくずれる場合は表示を PM と相談)。

#### B スタート隊形(M)
- 目的変数は**実際の ST**(result の `start_timing`。フライングは負の値、出遅れ・欠場は除く)。
- 出す確率:
  - 各艇が **すぐ内側の艇より先に出る確率**(ST が小さい確率。1コースは無し)
  - **カド(4コース)が3コースより先に出る確率**
  - **トップスタート(6艇で ST が最小)の艇の確率**(艇ごと、合計1)
- 作り方は M が決める(例: 各艇の ST の分布を予測し、組合せの確率を計算する)。評価: 各確率の logloss と較正、基準(コース別の過去の比率)との比較。前日版・直前版(展示 ST を使う)の両方。

#### C 展開の一言(M が型を選び、文言は `09` `tenkai.summary.*`)
- A・B の確率から、決まった型の短い文を1つ選ぶ(**AI による文章の生成はしない、断定語を使わない**)。
- 型の選び方の例: 逃げの確率が最大で 0.5 以上 → 「イン逃げ有力」型、カドが先に出る確率 0.5 以上かつ4コースのまくりが上位 → 「カドまくり警戒」型、トップスタートの確率が外側の艇で最大 → 「外のスタートに注目」型、どれでもない → 「混戦」型。しきい値は M が valid で決め、`analytics_rules` 相当の定数として固定する。
- 文にする値は確率の数字(%)と艇番だけ。

#### D 展開ごとの有力な組合せ(後回し)
- 展開(A の型)ごとの、条件付きの3連単の上位などは、A・B が安定してから検討する。

#### 公開JSON(E。`prediction.tenkai` に追加)

```json
"tenkai": {
  "nige": 0.552, "...": "...(3.2 のとおり)",
  "by_boat": [{"entry": 1, "course": 1, "nige": 0.552},
              {"entry": 4, "course": 4, "makuri": 0.071, "makurisashi": 0.032}],
  "start": {"ahead_of_inner": {"2": 0.41, "3": 0.38, "4": 0.52, "5": 0.33, "6": 0.30},
            "kado_ahead_of_3": 0.52,
            "top_start": {"1": 0.22, "2": 0.15, "3": 0.14, "4": 0.24, "5": 0.13, "6": 0.12}},
  "summary": {"type": "kado_makuri", "params": {"entry": 4, "pct": 52}}
}
```

- `by_boat`: 確率 0.01 以上の (艇, 決まり手) だけを艇ごとに載せる(小数3桁)。`start`: 小数2桁、キーは予定コース(`ahead_of_inner`)または枠番(`top_start`)。`summary`: 型の ID と差し込む値だけ(文はフロントが `09` の型で作る)。
- サイズ: 1レース約0.5KB、150レースで約+75KB(gzip後 約+10KB)。04 の見直し基準(gzip後300KB)に収まる。

#### 画面(DA・DB・W。S2 の展開予想ブロックを拡張)
1. **一言を先頭**(`tenkai.summary.*`)。
2. 艇ごとの決まり手の表(艇 × 主な決まり手の確率。小さい値は省略)。
3. スタート隊形(内側より先に出る確率を、コースの並びの図で。カドの確率、トップスタートの確率)。
4. 注意書き: 着順の確率とは別のモデルで計算していること(`tenkai.note`)。

| コース別(1〜6) | 出走数、1着率、決まり手別の率(逃げ・差し・まくり・まくり差し)、2着率、3着率、平均ST(style 集計 `h_cs_*_all`、縮小後の値) | 自前の集計 |
| 選手単位 | フライング率、出遅れ率、前付け率 | 自前の集計 |
| 今節 | 今の節の、前日までの各レースの着順(日付、R、進入コース、着順、決まり手) | 結果から自前で作る(1節 最大十数件) |
| 直近 | 直近10走の着順(日付、場、着順) | 同上 |

- **公開の範囲**: 公式の生データを丸ごと出さない。出すのは、上の表の出走表の項目(既に公開JSONに出している範囲)と、**自前で集計した率・件数**、着順の短い一覧(結果の事実。直近10走・今節に限る)だけ。年齢・体重・出身地・モーター番号ごとの生の履歴は出さない。
- 件数の少ない率(例: 出走数 10 未満のコース)は、件数と一緒に出し、アプリで薄く表示する(08 4章)。

### 4.2 ファイルの持ち方とサイズ

- **日ごとの別ファイル** `docs/data/racers/YYYYMMDD.json`(その日に出走する選手だけ)。選手カードを開いたときに初めて読み込む(`days` のファイルを重くしない)。
  - 1日の出走選手は約600〜700人。1人あたり約1.5KB → **約1MB/日(gzip後 約150KB)**。
  - 選手ごとの別ファイル(約1,600ファイルを毎日更新)は、コミットと公開の変更が多くなるので採らない。
  - 保管: 当日と前日の2日分だけを置き、古いものは消す(リポジトリの肥大化を防ぐ。U5)。過去日のレースから開いたときは「この日の選手カードはありません」。
- キー: `racers[<登録番号>]`。`days` の `boats[].racer_number` で引く。

### 4.3 表示(DA-6・W-16)

- S2(と S1 の場で絞る表示)で選手名をタップ → 下から出るシート、または別画面。
- 並び: 基本 → 今節の着順 → コース別(今回の予定コースを強調) → 当地 → 直近10走 → 選手単位の率。
- 件数の併記、少ない件数は薄く。「自前の集計で、公式の成績とは計算の仕方が違う」ことを注記する(`09` `card.*`)。
