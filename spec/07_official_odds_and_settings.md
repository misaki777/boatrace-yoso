## 1. 規約の確認(2026-11-03 実施)

確認したもの: `https://www.boatrace.jp/robots.txt`(1回)、サイトポリシー `https://www.boatrace.jp/owpc/pc/extra/policy.html`(1回)、オッズページ3種(1レース分、2026-11-02 戸田1R、間隔1.6秒)。

| 項目 | 内容 | 本ツールへの影響 |
|---|---|---|
| robots.txt | `User-agent: *` / `Disallow:`(空) = 全パスでクロールを禁止していない | 取得そのものは robots.txt 上は問題ない |
| 自動取得の明示的な禁止 | サイトポリシーに、スクレイピング・クローラ・プログラムでの取得を名指しで禁止する条文は無い | — |
| 禁止事項5 | 「不正アクセス、大量の情報送受信及び大量のアクセスなど、本サイトの運営に支障を与える行為」を禁止。違反と判断されたら事前通知なく利用停止もありうる | **取得量を最小にし、逐次・低頻度にする**(2章)。止められたらすぐ止まる仕組みを入れる |
| 著作権 | 掲載物は財団などの著作権で保護される。「私的使用など法律によって認められる範囲を超えて、無断で使用(複製、改ざん、頒布などを含む。)することはできません」 | **本人が自分の端末で見る私的使用は可と読める。公開リポジトリやGitHub Pagesでオッズの数値を配る(頒布)のは、許諾なしでは避けるべき** |
| リンク | 原則としてトップページへリンクする。フレーム内での表示などはお断り | PWAから公式サイトへリンクする場合はトップページにする。iframeで埋め込まない |
| 免責 | 正確性を保証しない | 既存の注意書き(非公式の参考情報)で足りる |

なお、オッズの数値そのものは事実の情報で、著作物には当たらないという考え方もある。ただし、規約が「無断使用(頒布を含む)」を広く禁じているので、**本ツールは保守的に「締切前オッズの数値は公開しない」を既定とする**。法的な判断ではなく、運用方針として決めるもの。

### 結論と方針

1. **取得**: 可。私的使用として、本人のPC(WSL)からローカルで手動か常駐ループで取る。量は「1レース1回、取る券種は必要最小限」に抑える。**GitHub Actions(公開リポジトリ)からは取得しない**(Phase 3 でも、Actions に含めるかは改めて決める)。
2. **保存**: `data/raw/official_odds/`(git管理外)。
3. **公開JSON(`docs/data/`)**: 締切前オッズの **数値は出さない**。出すのは、本ツールが計算した確率と、オッズから作った **粗い区分(期待値のランク)と取得時刻だけ**(数値のオッズを逆算できない粒度にする)。
4. **ローカルJSON(`docs/data-local/`、git管理外)**: オッズと期待値の数値を入れる。PCで `python -m http.server` を立て、同じWi-Fiにつないだスマホから見る「ローカル表示」で使う(5章)。
5. 既に決めた `final_odds`(turnmarkの確定オッズ。数値を推奨買い目の分だけ公開する。04 4章)も出所は同じ公式サイトなので、**同じ方針にそろえて、公開JSONからは数値を外す**(E-4 の変更。6章)。払戻金(的中した組合せの金額)は、新聞などでも広く報じられる結果の事実で量も少ないので、現状どおり公開する。
6. 利用者が数値の公開を望む場合は、BOATRACE振興会の許諾を得てから、エクスポートの設定 `PUBLISH_ODDS_NUMERIC`(既定 False)で切り替える(利用者確認事項 Q1)。

## 2. 締切前オッズの取得設計(C-5)

### 2.1 対象ページ(2026-11-03 に実物で確認)

URLの形はどれも `https://www.boatrace.jp/owpc/pc/race/{page}?rno={R番号}&jcd={場番号2桁}&hd={YYYYMMDD}`。

| page | 券種 | `td.oddsPoint` の数 | 1回の応答 | 既定で取るか |
|---|---|---|---|---|
| `odds3t` | 3連単(120通り) | 120 | 約45KB、**約10秒** | ○ |
| `odds2tf` | 2連単(30)+2連複(15) | 45 | 約40KB、約9秒 | ○ |
| `oddstf` | 単勝(6)+複勝(6、`下限-上限`) | 12 | 約34KB、約10秒 | ○ |
| `odds3f` | 3連複(20) | — | 未確認 | ×(設定で選べるようにはする) |
| `oddsk` | 拡連複(15、下限-上限) | — | 未確認 | × |

- 応答が1件あたり約9〜10秒かかった(WSLから。サーバー側が遅いのか経路が遅いのかは未確認)。所要時間の見積もりは、これを前提にする。
- オッズの時点の表示(C-5 で実物を確認済み。2026-11-03): **締切前は `<p class="tab4_refreshText">オッズ更新時間 HH:MM</p>`、締切後は `<p class="tab4_time">締切時オッズ</p>`**。どちらかの文字列をそのまま `odds_time_label` に保存し、「締切時」を含むかどうかで `is_final_odds` を決める。

### 2.2 HTML解析(標準ライブラリ `html.parser`)

- `td` の class に `oddsPoint` を含むセルの文字列を、文書の順に集める。数値でない値(欠場の空欄や `-` など)は null にする。**`0.0` は「票が無い」ことを表すので、これも null にする**(期待値の計算で0倍として扱わないため)。
- **3連単(`odds3t`)の並び**(実物で確認済み): 列が1着の艇(1〜6)、行のブロックが2着の艇、ブロックの中の行が3着の艇。文書の順の i 番目は次のように対応する。

```
idx = 0
for b in range(5):            # 2着: 1着以外の艇を昇順に並べたときの b 番目
    for r in range(4):        # 3着: 1着・2着以外の艇を昇順に並べたときの r 番目
        for first in 1..6:    # 列
            second = others(first)[b]
            third  = others(first, second)[r]
            odds[f"{first}-{second}-{third}"] = cells[idx]; idx += 1
```

  検算: 2026-11-02 戸田1R で `2-1-6` = 27.5、払戻 2,750円(公式の結果と一致)。
- **2連単・2連複(`odds2tf`)**: 前半30セルが2連単(`for r in range(5): for first in 1..6: second = others(first)[r]`。検算: `2-1` = 4.9、払戻490円と一致)、後半15セルが2連複。**2連複の並びは、表の左下の三角を列ごとに読む順: `1=2, 1=3, 2=3, 1=4, 2=4, 3=4, 1=5, …, 5=6`**(C-5 で確認済み。検算: 2026-11-02 戸田1R の `1=2` = 2.7、払戻270円と一致)。
- **単勝・複勝(`oddstf`)**: 前半6セルが単勝(1〜6号艇の順)、後半6セルが複勝(`"1.0-1.0"` のような `下限-上限` の形)。
- 出力の形は turnmark の `odds` と同じ入れ子の dict にする(interim の odds の展開をそのまま使えるようにする。`02_features.md` 1.4)。
- 解析のテストはネットワークを使わずに行う。**公式サイトのHTMLそのものはリポジトリに入れない**(公開リポジトリでの再配布になるため。2026-11-03 追記)。テスト用には、構造(タグ・class・セルの並び)だけを残し、選手名を消して数値を架空の値に置き換えた **合成HTML** を `tests/fixtures/official_odds/` に置く(9.5)。実物のHTML(`data/raw/official_odds/`、git管理外)を使うテストは、ファイルがあるときだけ動かす(無ければ skip)。**HTMLの構造が変わったら解析を失敗させる**(セル数が120・45・12と違えばエラー。間違った値を黙って出さない)。

### 2.3 取得タイミング

- **1レースにつき1回、締切の N 分前(既定 N=5)** に、設定した券種のページを順に取る。
  - 予想(前日モデル・直前モデル)は先に出しておき、オッズは期待値の計算だけに使う。
  - N=5 にするのは、直前情報(締切の30〜7分前)が出たあとで、かつ投票が間に合う時間を残すため。設定で3〜15分にできる。
- 締切時刻は openapi の出走表の `closed_at` を使う。遅れなどで変わることがあるので、常駐ループは openapi の当日分を **30分ごと**に取り直す(openapi側の更新は約10分間隔。収集担当の既存ルールの範囲内)。
- スケジューラ: 対象レースを「取得予定時刻 = closed_at − N分」の順に並べ、1本の作業で順に処理する(並列にしない)。各レースの取得の窓は [closed_at − (N+3)分, closed_at − 2分]。窓に間に合わなかったレースは取らずに `late` と記録する(締切後のオッズを取りに行かない)。
- 中止・順延のレースは取らない。**欠場艇がいるレースは取る**(他の艇の組合せのオッズは有効なため)。欠場艇を含む組合せのオッズは null になる(2026-11-03 承認。実サイトでの欠場艇の表示は未確認なので、最初に出会ったときに解析結果を確かめる)。

### 2.4 リクエスト数と所要時間の見積もり

前提: 1日150レース(2026-11-02 は13場・156レース。24場すべてが開く日は最大288レース)、リクエストの間隔1.5秒以上、応答は1件約10秒。

| 設定 | 1日のリクエスト数 | 1レースあたりの所要時間 | 1日の合計時間 |
|---|---|---|---|
| **既定: 3ページ(3連単・2連単/複・単複)** | 156×3 = **468** + openapi 約26 ≒ **約500** | 3 × (10 + 1.5) ≒ 35秒 | 約1.5時間(最初の締切 8:35 から最後の締切までに分散。ミッドナイト開催のある日は最後の締切が22時台になり、約14時間。平均で約2分に1回) |
| 3連単だけ | 約180 | 約12秒 | 約35分 |
| 全5ページ | 約810 | 約58秒 | 約2.5時間 |
| 対象を絞る(お気に入りの場だけ、推奨ありのレースだけ) | 上の数 × 対象の割合 | 同上 | |

- 混み合う時間帯: 13場が開く日でも、締切は1レースあたり平均2分に1回程度。1レース35秒なので処理は追いつく。ただし、締切が1分以内に重なることがあるので、窓(2.3)に余裕を持たせ、間に合わないものは `late` にする。
- 上限: `--max-requests-per-day`(既定600)。超えたらその日は止める。

### 2.5 負荷への配慮と停止条件

- **同時接続は1本**。リクエストの間隔は1.5秒以上(`--sleep`。1.0未満はエラー)。間隔には応答の待ち時間を含めない(応答が終わってから1.5秒空ける)。
- User-Agent は既存の `boatrace-yoso/0.1 (personal use)`。
- 同じページを同じレースで2回取らない(リトライを除く)。リトライは5xx・タイムアウトだけで、1回まで(締切に間に合わなくなるので、01章の3回より少なくする)。
- **HTTP 403・429、または3回続けて失敗したら、その日の取得をすべて止める**。ログに `stopped` と記録し、再開は手動にする(相手から止められたサインとして扱う)。
- Cookie やログインは使わない。画像・CSS・JavaScriptは取らない(HTMLだけ)。

### 2.8 統合スクリプト `scripts/live_loop.py`(P-2。2026-11-03 実装)

- 起動: `source .venv/bin/activate` → `python -m scripts.live_loop [--dry-run | --prepare-only | --no-odds | --skip-prepare]`。オプションの `--minutes-before`・`--pages`・`--stadiums`・`--race-ids-file`・`--sleep`・`--resume` は、そのまま `src.collect.official_odds --loop` に渡す。`--only-recommended` はスクリプト側のオプションで、準備で書き出した `docs/data/days/YYYYMMDD.json` から推奨買い目のある race_id を一時ファイルに書き、`--race-ids-file` で渡す(2026-11-03 修正)。
- 各担当のモジュールは **CLI として子プロセスで呼ぶだけ**(中身を import しない。読むのは `raw_io.load_raw` で当日の締切時刻を知るときだけ)。スクリプト自身は通信しない。
- 流れ: (1) 準備 `fetch(openapi) → build_interim → build_features(pre) → predict(pre) → export_day → export_index`。途中で失敗したら残りを実行しない (2) `official_odds --loop` を子プロセスで起動(**取得のスケジュールと待機は収集担当の側だけが持つ**) (3) 30秒ごとに `data/raw/official_odds/YYYY/YYYYMMDD/*.json.gz` の更新を見て、増えたら `export_day --date D --odds-only` (4) 30分ごとに結果反映 `fetch(openapi) → build_interim → export_day → export_index`(openapi の再取得は fetch が10分以内ならスキップする) (5) 最後の締切の40分後に最後の結果反映をして終わる。Ctrl+C でも子プロセスを止めて終わる。
- **各担当への前提(インターフェース)**:
  - C-5: `python -m src.collect.official_odds --date D --loop` が、当日分を取り終えるか、停止条件(2.5)で止まったら終了コード(0/1/2)を返して終わること。SIGTERM で速やかに終わること。**`_stopped.json` がある日は、スクリプトはオッズ取得を起動せず(`--resume` を付けたときだけ起動する)、結果反映だけ続ける**。止まった理由の確認と再開は、利用者が手動で行う。
  - E-8: `python -m src.export.export_day --date D --odds-only` に対応すること。未対応の間(argparse のエラー=終了コード2)は、スクリプトが通常の `export_day` で代わりに更新する。
  - M: `python -m src.model.predict --date D --variant pre` が、`models/latest` を使って動くこと。
- 子プロセスには `LD_LIBRARY_PATH` に `.venv/lib/extra`(libgomp)を足して渡す(U9)。
- 安全側の入力チェック: `--sleep` は1.0以上、`--minutes-before` は3〜15、`--refresh-minutes` は10以上。
- テスト: `tests/common/test_live_loop.py`(コマンドの組み立て・締切時刻の読み取り・入力チェック。通信も子プロセスの実行もしない)。

## 3. 期待値の計算と公開範囲(E-5/E-6)

### 3.1 計算

- 予想の確率 `prob`(picks の各組合せ)と締切前オッズから、`ev = prob × odds` を計算する。
- 複勝・拡連複は下限のオッズを使う(保守的にするため)。
- 欠場艇がいるときは、確率を欠場艇を除いて正規化し直してから計算する(`combinations.py`)。
- オッズが取れなかった組合せ(欠場など)は `ev = null`。

### 3.2 期待値のランク(公開JSONに出す粗い区分)

| `ev_rank` | 条件 | 意味 |
|---|---|---|
| `A` | ev ≥ 1.20 | 期待値が大きくプラス |
| `B` | 1.00 ≤ ev < 1.20 | プラス |
| `C` | 0.80 ≤ ev < 1.00 | 少しマイナス |
| `D` | ev < 0.80 | マイナス |
| null | オッズが無い | |

ランクの境界はエクスポートの設定 `EV_RANK_BOUNDS` に置く。公開JSONではランクだけにし、ev の数値・オッズの数値は出さない(数値は `prob` から逆算できてしまうため)。

### 3.3 JSONの追加項目

レースの `prediction` に `odds_snapshot` を追加する。

```json
"odds_snapshot": {
  "fetched_at": "2026-11-03T10:40:12+09:00",
  "minutes_before_close": 4.8,
  "pages": ["odds3t", "odds2tf", "oddstf"],
  "status": "ok"
}
```

`status`: `ok` / `partial`(一部のページだけ取れた) / `late`(間に合わず未取得) / `failed`(要求したページがすべて失敗。2026-11-03 追加) / `not_targeted`(対象外の場・レース。`_targets.json` から判定) / `stopped`(取得を止めた日)。オッズを取っていない日やレースでは、`odds_snapshot` そのものを null にする。

picks と recommended の各要素に追加する項目:

| 項目 | 公開JSON(`docs/data/`) | ローカルJSON(`docs/data-local/`) |
|---|---|---|
| `ev_rank` | ○ | ○ |
| `odds`(締切前) | ×(出さない) | ○ |
| `ev` | ×(出さない) | ○ |

- ローカルJSONは公開JSONと同じスキーマで、上の2項目と `final_odds` の数値が多いだけにする(フロントは同じ処理で両方を読める)。置き場所は `docs/data-local/days/YYYYMMDD.json` と `index.json`。**`.gitignore` に `docs/data-local/` を追加する(P-2)**。
- サイズの増え方: picks は1レース36要素(単勝6、2連単10、3連単20)。`ev_rank` を足すと1要素あたり約15バイト、1レースで約0.6KB、150レースで約+90KB(gzip後は約+10KB)。picks の深さは変えない(4.3)。

### 3.4 表示上の注意(デザイナー・フロント)

- オッズの取得時刻を必ず添える(例: 「10:40時点(締切5分前)のオッズで計算」)。
- 「締切前のオッズは締切までに変わる。確定オッズ(払戻の倍率)とは違う」ことを、期待値の近くに注記する。
- 投票の判断は投票アプリの最新のオッズで行うよう促す。必要オッズ(1/prob)の表示は残す(オッズが無くても使えるため)。

## 4. 推奨買い目の設定(S6、W-7)

### 4.1 方式: フロントで picks から計算し直す

- **方式**: エクスポートは既定の戦略で `recommended` を1つ出す(今と同じ)。設定画面で利用者が条件を変えたら、**フロントが picks(確率上位の一覧)と ev_rank から、その端末だけで推奨買い目を計算し直す**。
- 理由: (a) 設定の組合せは無数にあり、export で複数の戦略を出すとJSONが大きくなる。(b) 設定は本人の端末にだけあればよく、サーバー側の処理は無い(静的サイト)。(c) 戦略の計算は単純な絞り込みなので、ブラウザで十分に速い。
- 計算のルールをPythonとJavaScriptで二重に持つことになるので、**エクスポート担当が `docs/data/sample/strategy_cases.json`(入力の picks と設定、期待される推奨買い目の組)を作り、フロントのテストとPythonのテストの両方で同じケースを使う**。

### 4.2 設定項目

| 項目 | 選択肢 | 既定 |
|---|---|---|
| 券種 | 単勝・2連単・3連単(複数選択可) | 3連単 |
| 点数 k(券種ごと) | 単勝 1〜3、2連単 1〜10、3連単 1〜20 | 3連単 5 |
| 最低確率 θ(この確率未満の組合せは買わない) | なし / 1% / 2% / 3% / 5% | なし |
| 見送り: 堅さ | なし / 「荒」なら見送り / 「中」以下なら見送り(堅さの区分は 05 3章の固定しきい値) | なし |
| 期待値で絞る | なし / ランクB以上(ev ≥ 1.0) / ランクAだけ(ev ≥ 1.2) | なし |
| オッズが無いとき(期待値で絞る設定のとき) | 確率だけで選ぶ / 見送る | 確率だけで選ぶ |
| 1点あたりの金額(表示用) | 100〜1,000円(100円単位) | 100円 |

- 適用の順序: 券種ごとに picks を確率の降順 → θ 未満を除く → 期待値の条件で除く → 上位 k 点 → 堅さの見送りなら全部を除く。
- 設定は端末の localStorage に保存する(キー `settings.v1`)。読めない・壊れているときは既定に戻す。
- 既定の戦略と同じ設定のときは、export の `recommended` をそのまま表示する(計算結果が一致することをテストで保証する)。
- 1点あたりの金額は、表示用の「投資額・払戻額の試算」にだけ使う。実際の購入とは関係しない。

### 4.3 picks の深さ

設定で選べる最大の点数は picks の深さ以内にする: 単勝6、2連単10、3連単20(今と同じ)。θ と期待値の条件で絞るので、上位20点より下まで必要になることは少ない。深さを増やすとJSONが大きくなるため変えない(3連単を40点にすると、150レースで約+150KB)。

### 4.4 成績画面(S3)との関係

- S3 の集計(`performance.json`)は、**既定の戦略(export の `recommended`)だけで出す**。設定とは切り離す。
- 設定を既定から変えているときは、S3 に「成績は既定の買い方(3連単 上位5点)で集計しています。今の設定とは違います」と表示する。
- Phase 2b(任意): 読み込み済みの日のファイル(`result.order` と `result.payouts`)から、今の設定での成績をフロントで試算する「設定での試算」を S3 に出す。期待値の条件を含む試算は、`ev_rank` がある日だけで行い、その旨を表示する。

## 7. モデル側(M)で必要なこと

1. **バックテストの注意**: 過去の締切前オッズは無い(取り始めた日から貯まる)。それまでは確定オッズを「締切前オッズの代わり」に使うしかなく、これは後知恵になる(確定オッズは締切後にしかわからない)。S3(`ev_final`)・S4(`ev_final_haircut`)は、引き続き参考値(`leak_free: false`)として扱う。
2. **オッズの変動の分析(M-7)**: 締切前オッズが1〜2週間分貯まったら、締切N分前のオッズと確定オッズ(turnmark)を比べ、券種別・人気順別の変化率(確定 ÷ 締切前)の分布を出す。これで S4 の割引率(0.85倍)を実測の値に置き換える。
3. **フォワードテスト(M-8)**: 締切前オッズで期待値の戦略(EV ≥ τ)を選び、確定の払戻で回収率を出す。これはリークの無い評価になる。日々の結果を `reports/forward/` に貯める。期待値の戦略を既定にするかどうか(U2)は、ここで1か月程度の結果を見てから決める。
4. **較正の確認**: 期待値は確率の較正に強く左右される(03 5章)。ランクA(ev ≥ 1.2)の買い目について、予測した確率と実際の的中率の差を M-8 で毎月確かめる。

## 9. レースを選んだときにオッズを取る中継 Worker(2026-11-03 追加)

### 9.1 決定事項と位置づけ

| 方式 | 役割 | 状態 |
|---|---|---|
| **中継 Worker(本章)** | **主な方式**。スマホでレースを選んで「オッズを取る」を押したときに、そのレースの締切前オッズを取って、スマホにだけ返す | Cloudflare Workers の無料枠を使う(利用者承認済み)。アカウントの作成とデプロイは利用者が後で行う |
| 一括取得モード(収集担当に指示済み) | GitHub Actions から1回起動して、N分以内に締切のレースを取って終わる。期待値ランクの表示と成績の記録用 | GitHub への移行は後で。ログにオッズの数値を出さない |
| PC常駐ループ(2章・P-2) | 当面の運用と、オッズ変動の分析用データ(M-7・M-8)の蓄積 | 残す |

```
スマホ(PWA) ──GET /odds(合言葉ヘッダ)──→ Cloudflare Worker ──(最大3ページ、順番に)──→ www.boatrace.jp
     ↑                                         │  KVキャッシュ(60秒)・1日の上限・停止フラグ
     └──────── 解析済みのオッズJSON ←───────────┘
     期待値・推奨買い目はスマホで計算(公開JSONの picks の確率 × 受け取ったオッズ)
```

- 締切前オッズの数値は **Worker からスマホに返すだけ**。公開JSON・リポジトリ・Worker のログには残さない(1章の方針を維持する)。
- 期待値はスマホ側で、公開JSONの確率上位(picks)と組み合わせて計算する(9.6)。

### 9.2 API

```
GET https://<worker名>.<アカウント>.workers.dev/odds?date=20261103&jcd=02&rno=1&types=3t,2tf,tf&closed_at=2026-11-03T10:45:00%2B09:00
X-Odds-Key: <合言葉>
```

| パラメータ | 必須 | 内容 |
|---|---|---|
| `date` | ○ | `YYYYMMDD`。**JSTの今日だけ受け付ける**(過去日・未来日は 400) |
| `jcd` | ○ | 場番号 `01`〜`24` |
| `rno` | ○ | R番号 `1`〜`12` |
| `types` | 任意 | `3t`(odds3t)・`2tf`(odds2tf)・`tf`(oddstf)をカンマ区切りで。既定は3つすべて。**それ以外の値は 400**(3連複・拡連複は今は扱わない) |
| `closed_at` | ○ | そのレースの締切時刻(公開JSONの `closed_at`)。Worker はこれを過ぎていれば公式サイトに取りに行かない(9.3) |

成功時(200):

```json
{
  "ok": true,
  "race_id": "20261103-02-01",
  "fetched_at": "2026-11-03T10:40:12+09:00",
  "cached": false,
  "cache_age_sec": 0,
  "pages": {"3t": "ok", "2tf": "ok", "tf": "ok"},
  "odds_time_label": "…",
  "is_final_odds": false,
  "odds": {
    "trifecta": {"1": {"2": {"3": 9.2}}},
    "exacta": {"1": {"2": 4.6}},
    "quinella": {"1": {"2": 3.1}},
    "win": {"1": 1.8},
    "place": {"1": {"lower_limit": 1.0, "upper_limit": 1.0}}
  },
  "quota": {"used_today": 123, "limit_per_day": 300}
}
```

- `odds` の形は C-5 の解析結果(2.6)と同じ。`pages` は券種のページごとの状態(`ok` / `cached` / `error` / `parse_error`)。一部だけ失敗したときも 200 で返し、失敗した券種は `odds` に入れない。
- `fetched_at` は公式サイトから取った時刻(キャッシュから返したときも、元の取得時刻)。

失敗時は `{"ok": false, "error": "<コード>", "message": "<日本語の説明>"}`:

| HTTP | `error` | 場面 | スマホの表示(9.7) |
|---|---|---|---|
| 400 | `bad_request` | パラメータの誤り・今日以外の日付 | 「取得できません(要求の誤り)」 |
| 401 | `unauthorized` | 合言葉が無い・違う | 「合言葉を確認してください」→ 設定へ |
| 403 | `forbidden_origin` | 許可していないオリジン | (開発時のみ起きる想定) |
| 409 | `closed` | `closed_at` を過ぎている | 「締切後のため取得しません。確定オッズは翌日に反映されます」 |
| 429 | `daily_limit` | 1日の上限に達した | 「今日の取得上限に達しました」 |
| 502 | `upstream_error` | 公式サイトの 5xx・タイムアウト・解析の失敗 | 「公式サイトから取得できませんでした」+ 再試行 |
| 503 | `stopped` | 公式サイトから 403・429 を受けて、その日の取得を止めている | 「今日は取得を停止しています」 |

### 9.3 公式サイトへの負荷対策

1. **キャッシュ**: 同じレース・同じ券種のページは **60秒間** 使い回す(取りに行かない)。キャッシュは **Workers KV**(`expirationTtl: 60`。KV の TTL の最小値が60秒)に、解析後のJSON(数値のみ。HTMLは入れない)で入れる。Cache API は workers.dev のドメインでは効かない場合があるので使わない(R-1 で確かめ、使えるなら置き換えてよい)。
2. **1回の要求で取るのは最大3ページ**。**順番に**取り、ページの間は **1秒以上** 空ける(`await` で待つ。待ち時間は CPU 時間に数えられない)。並列に取らない。
3. **1日の上限**: 公式サイトへの取得のページ数で **300**(既定。環境変数 `DAILY_LIMIT`)。キャッシュから返した分は数えない。100レース × 3ページに相当。KV のキー `count:YYYYMMDD` で数える(KV は結果整合なので、上限は多少ずれることがある。安全側の目安として扱う)。
4. **締切後は取らない**: `closed_at` を過ぎた要求は 409 で断る。結果が確定した後のオッズは、翌日の確定オッズ(turnmark)で足りる。取ったページに「締切時」の表記があったときも、`is_final_odds: true` を付けて返し、それ以上は取らない。
5. **停止**: 公式サイトから 403・429 が返ったら、KV に `stopped:YYYYMMDD` を書き、その日は以後すべて 503 で返す(2.5 と同じ考え方)。解除は翌日(JST)になるか、利用者が KV のキーを消したとき。
6. スマホ側も、取得中はボタンを押せないようにし、同じレースの再取得は60秒たつまでボタンを無効にする(余計な要求を Worker に送らない)。
7. User-Agent は `boatrace-yoso-proxy/0.1 (personal use)`。Cookie は使わない。HTMLだけを取る。

### 9.4 Workers 無料枠に収まるか

| 制約(無料枠) | 本ツールでの見込み | 判断 |
|---|---|---|
| 要求数 10万/日 | 1日に数十〜数百 | 十分に収まる |
| **CPU時間 10ms/要求** | 公式サイトの応答待ち(約10秒×3)は CPU 時間に数えない。CPU を使うのは HTML の解析だけ。約40KBのHTMLから必要な部分を切り出し、正規表現でセルを拾う方法なら、1ページ1ms程度の見込み(R-1 で `performance.now()` 相当の計測をして確かめる) | 収まる見込み。**DOMパーサーや HTMLRewriter で全体をなめる方法は使わない** |
| サブリクエスト 50/要求 | 公式サイトへ最大3 | 収まる |
| KV: 読み取り 10万/日、書き込み 1,000/日 | 1回の取得で書き込みは キャッシュ最大3 + カウンタ1。上限300ページなら書き込みは約400/日 | 収まる。**上限を増やすときは KV の書き込み数(1,000/日)に注意** |
| 実行時間 | クライアントがつながっている間は、応答待ちで打ち切られない | 約30秒かかる。スマホ側のタイムアウトは45秒 |

HTMLの解析をCPU時間内に収める方法:
1. `response.text()` で受け取る(40KB程度)。
2. 券種の見出し(`<span class="title7_mainLabel">`)の最初の位置から、券種の数だけ、その後の `</table>` までを `indexOf` で切り出す(ヘッダ・メニュー・**レース情報の表(ページ内の最初の `div.table1`。2026-11-03 C-5 の指摘で訂正)**は解析しない)。
3. 切り出した範囲で `/<td class="oddsPoint[^"]*">([^<]*)<\/td>/g` を回してセルを集める。オッズ時点は、締切前・締切後の両方の表記に対応する `/<p class="tab4_(?:refreshText|time)">([^<]*)<\/p>/` で拾う(2.1)。`0.0` は null(2.2)。
4. セル数が120・45・12でなければ `parse_error`(Python と同じく、黙って間違った値を返さない)。

**未確認のリスク**: Cloudflare のデータセンターからの接続を、公式サイト側が拒否する(または応答が極端に遅い)可能性がある。R-1 のデプロイ後の最初の確認項目にする。拒否された場合は、PC常駐ループとローカル表示に戻る。

### 9.5 解析ロジックの一致(Python と JavaScript)

- 共通のテストデータ: `tests/fixtures/official_odds/`(**収集担当が作る**。中継担当は読むだけ)
  - `odds3t.synthetic.html`、`odds2tf.synthetic.html`、`oddstf.synthetic.html`: 合成HTML(2.2の注記。構造は実物と同じで、数値は架空、選手名は消す)。欠場で空欄のセル、`締切時オッズ` と締切前の表記の両方の例を含める
  - `*.expected.json`: それぞれの期待される解析結果(2.6 の `odds` の形)
  - `broken_*.html`: セル数が足りないなど、解析が失敗すべき例
- Python(`tests/collect/`)と JavaScript(`workers/odds-proxy/test/`)の両方で、同じファイルを読んで期待値と一致することを確かめる。どちらかの解析を直したら、もう一方のテストも必ず通すこと。
- 実物のHTMLとの一致は、`data/raw/official_odds/` にファイルがあるときだけ動くテスト(skip 可)で確かめる。

### 9.6 期待値と推奨買い目の再計算(スマホ側)

- Worker から受け取ったオッズと、公開JSONの picks の `prob` から、`ev = prob × odds` を計算し、3.2 の境界で `ev_rank` を付ける。複勝は下限のオッズを使う(3.1 と同じ)。
- 推奨買い目は、W-8 の計算(4.2 の設定と適用順)に、このオッズで計算した ev を入れて計算し直す。**E-9 の `strategy_cases.json` に「数値のオッズを入力に含むケース」を加え、フロントとPythonの両方で同じ結果になることをテストする(E-10)**。
- オッズの優先順位: (1) 手入力(S7) → (2) Worker で取ったオッズ → (3) 公開JSONの `ev_rank`(一括取得モードで作られたもの) → (4) オッズなし(必要オッズだけ表示)。
- 取得したオッズは **端末のメモリと sessionStorage にだけ** 置き、localStorage やサーバーには保存しない。日付が変わったら捨てる。
- 数値のオッズや ev を、スマホから外部に送らない。

### 9.8 認証と CORS

- 合言葉: スマホの設定画面で入力し、端末の localStorage に保存する。要求のたびに `X-Odds-Key` ヘッダで送る。Worker 側は Workers の secret `ODDS_KEY`(`wrangler secret put` で設定)と、時間が一定になる比較で照らし合わせる。合言葉はリポジトリ・公開JSON・URL のクエリに入れない。
- CORS: `Access-Control-Allow-Origin` は、環境変数 `ALLOWED_ORIGINS`(カンマ区切り)に一致するオリジンだけに返す。既定の候補:
  - `https://<GitHubのユーザー名>.github.io`(GitHub Pages を公開したとき)
  - `http://localhost:8000`、`http://127.0.0.1:8000`
  - **自宅Wi-Fiでのローカル表示(5章)では、スマホのオリジンは `http://192.168.x.x:8000` になる**。これを許可しないとローカル表示から使えないので、利用者がPCのLANのアドレスを `ALLOWED_ORIGINS` に足す(利用者確認事項 Q6)
- プリフライト(`OPTIONS`)に応答し、許可するヘッダは `X-Odds-Key` だけにする。
- CORS はブラウザ以外からの要求を防げないので、守りの本体は合言葉と1日の上限。

### 9.9 ログ

- Worker のログ(`console.log`)には、race_id・券種・状態・キャッシュかどうか・所要時間・その日の使用数だけを出す。**オッズの数値・合言葉・HTMLは出さない**。
- 一括取得モード(Actions)も同じ(数値を出さない)。

### 9.10 ファイル構成(中継担当 R)

```
workers/odds-proxy/
  README.md                 デプロイ手順(アカウント作成、KV の作成、secret の設定、ALLOWED_ORIGINS、動作確認、無料枠の確認方法)
  wrangler.toml.example     設定の雛形(KV の id・名前はプレースホルダ。実際の値は入れない)

  src/parse.js              HTML の切り出しと解析(Workers と Node の両方で動く純粋な関数)
  src/core.js               日付・締切の判定、キャッシュキー、上限の判定などの純粋な関数
  test/*.test.mjs           node:test のテスト(fetch と KV は差し替え用の偽物を渡す)
```

- npm と wrangler はこのリポジトリには入れない(package.json も作らない)。デプロイ時に利用者が `npx wrangler` を使うかどうかは、README で手順として示すだけにする。
- **ローカルのテスト**: このPCの Node は v16.20.0(nvm)。`node --test workers/odds-proxy/test/` は動くことを確かめた。ただし v16 には `fetch`・`Request`・`Response` が無いので、テストは純粋な関数(parse・core)と、偽物の `fetch`・`Response` を渡したハンドラに限る。Node 18 以上(`nvm install 20` で、sudo なしで入れられる)にすれば `Request`/`Response` を使ったハンドラのテストも書ける(追加の導入なので、利用者確認事項 Q7)。
